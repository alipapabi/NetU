# NetU 统一操作密码弹窗设计

日期: 2026-06-30

## 1. 目标

将 `preview / download / delete` 三类需要密码验证的操作统一到同一个页面内弹窗组件中，不再依赖浏览器原生 `prompt()`，也不再在缺少权限时把用户打断到独立登录页。

本次设计基于已确认的 `方案 A`：

- 点击 `预览 / 下载 / 删除` 后，直接弹出统一密码弹窗
- 用户输入正确密码后，服务端继续沿用现有能力 cookie，默认记住 `7 天`
- 不同操作共享同一个弹窗组件，但根据操作类型执行不同后续动作

## 2. 交互原则

### 2.1 统一入口

以下三类动作都走同一个页面内密码弹窗：

- `预览`
- `下载`
- `删除`

弹窗需要根据当前动作动态切换：

- 标题
- 说明文案
- 确认按钮文案
- 成功后的后续行为

### 2.2 权限记忆

用户输入一次正确密码后：

- 对应能力 cookie 写入浏览器
- 默认有效期为现有配置中的 `7 天`
- 后续相同能力操作在有效期内不再重复输入密码

权限记忆规则保持不变：

- `preview` 只覆盖预览
- `download` 只覆盖下载
- `delete` 只覆盖删除

## 3. 预览设计

### 3.1 当前页弹层预览

以下类型在输入正确 `preview` 密码后，直接在当前界面弹出预览层：

- 图片：`jpg` `jpeg` `png` `gif` `webp` `svg`
- 音频：`mp3` `wav` `ogg`
- 视频：`mp4` `webm` `mov`
- PDF：`pdf`
- 文本：`txt` `md` `json` `csv` `log` `py` `js` `css`

理由：

- 这些类型适合快速查看
- 当前页弹层更接近常见文件管理器的使用习惯
- 用户不需要离开当前列表页

### 3.2 新页面预览

以下类型在输入正确 `preview` 密码后，打开新页面预览：

- HTML：`html`
- Office：`doc` `docx` `xls` `xlsx` `ppt` `pptx`
- 其他复杂或不适合弹层承载的类型

理由：

- 复杂内容在新页中更稳定
- Office 和 HTML 的渲染、隔离和回退逻辑本来就更适合独立页面
- 当前页不必承载过重的预览逻辑

### 3.3 一般规律

本次预览规则采用以下通用判断：

- `轻内容`：适合当前页快速查看的，走弹层
- `复杂内容`：需要独立布局、隔离、转换或回退处理的，走新页面

如果某文件类型暂不支持当前页弹层预览，则优先退化为新页面预览；若仍不适合，则提示建议下载查看。

## 4. 下载设计

点击 `下载` 后：

- 若已有 `download` 能力 cookie，则直接触发浏览器下载器
- 若没有对应权限，则弹出统一密码弹窗
- 输入正确密码后，前端立即触发下载动作

下载行为要求：

- 不再跳转到登录页
- 不改变当前文件列表页上下文
- 使用浏览器原生下载器执行下载

推荐实现方式：

- 前端在认证成功后，创建隐藏 `<a>` 元素并触发点击
- 或使用 `window.location` / 新建隐藏 iframe 触发下载
- 以“拉起浏览器下载器”为目标，不做前端 Blob 中转

## 5. 删除设计

点击 `删除` 后：

- 若已有 `delete` 能力 cookie，则直接执行删除
- 若没有对应权限，则弹出统一密码弹窗
- 输入正确密码后，立即删除目标文件

删除成功后：

- 显示成功提示
- 刷新文件列表
- 若当前有搜索条件，保持搜索状态不丢失

删除失败时：

- 保留当前列表页
- 在页面内状态区显示错误信息
- 不使用浏览器原生弹窗

## 6. 统一弹窗组件设计

### 6.1 组件职责

统一弹窗组件只负责：

- 展示动作相关文案
- 收集密码输入
- 提交对应动作的能力验证
- 把验证结果交还给调用方

它不直接绑定某一类业务，而是由调用方传入：

- `mode`: `preview / download / delete`
- `filename`
- `title`
- `description`
- `confirmText`

### 6.2 组件状态

弹窗至少包含以下状态：

- 默认态
- 提交中
- 密码错误态
- 取消关闭态

### 6.3 组件交互

弹窗支持：

- 点击按钮打开
- 点击取消关闭
- `Enter` 确认
- `Escape` 关闭
- 点击遮罩关闭

错误提示在弹窗内部显示，页面级状态提示仍显示在主页面状态区。

## 7. 前后端协作方式

### 7.1 前端

前端统一封装一个动作执行函数，例如：

- `ensureCapabilityAndRun(mode, action)`

执行流程：

1. 判断当前是否已拥有能力 cookie
2. 若没有，则打开统一弹窗
3. 提交密码到现有登录接口
4. 登录成功后继续执行原动作
5. 登录失败则在弹窗内部报错

### 7.2 后端

后端权限模型保持不变，继续使用：

- `preview`
- `download`
- `delete`

本次只需要做小范围配合：

- 对前端密码提交返回更适合 AJAX 处理的结果
- 避免前端为了登录被迫依赖整页重定向语义

优先做法：

- 保留现有表单登录兼容逻辑
- 新增一个轻量 JSON 能力验证接口，供统一弹窗调用

## 8. 测试范围

需要补充的测试包括：

- 点击预览时不再跳到登录页，而是由页面内弹窗接管
- 图片/音频/视频/PDF/文本在当前页弹层预览
- Office/HTML 在验证成功后打开新页预览
- 点击下载时输入正确密码后触发浏览器下载
- 点击删除时输入正确密码后完成删除
- 弹窗不再使用 `window.prompt()`
- 已有能力 cookie 时不重复弹窗

## 9. 风险与取舍

- `下载` 的“浏览器下载器”触发方式受浏览器安全策略影响，因此需要选择稳定的原生下载触发方式
- `当前页弹层预览` 的类型不能过度扩张，否则会让主页面脚本和布局过重
- `复杂文件新页预览` 虽然多开一页，但更稳定、更容易维护

本次取舍是：

- 优先统一交互体验
- 优先保持现有权限模型不变
- 优先让轻内容更顺手、复杂内容更稳定

## 10. 验收标准

完成后应满足：

- `preview / download / delete` 共用一个页面内密码弹窗组件
- 页面中不再使用浏览器原生 `prompt()`
- 预览输入正确密码后：
  - 图片、音频、视频、PDF、文本走当前页弹层预览
  - Office、HTML 走新页面预览
- 下载输入正确密码后，直接拉起浏览器下载器
- 删除输入正确密码后立即删除并刷新列表
- 密码权限默认记住 `7 天`
