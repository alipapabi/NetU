# NetU 文件管理器安全改造设计

日期: 2026-06-30

## 1. 背景与目标

当前 NetU 是一个基于 Flask 的单体文件服务，主业务逻辑集中在 `file_downloader.py`。现有版本已经具备文件列表、密码登录、上传、下载、删除、预览和后台改密等基础能力，但存在以下问题：

- 路由、认证、页面模板、文件操作逻辑高度耦合，维护成本高
- 密码仍以明文方式保存在 `.passwords.yaml` 中，安全性不足
- 文件预览、下载、删除的权限边界不清晰，删除接口复用了上传权限
- `DOWN_DIR` 与部分展示文案写死路径，部署迁移困难
- 后台路由存在重复实现，容易引发行为冲突
- 预览接口缺少更严格的 MIME、CSP、沙箱和响应头控制
- 界面可用性一般，自动发现新文件能力较弱

本次改造采用“保留 Flask 单体部署，但做轻量模块化重构”的方案，目标是：

- 访问首页前必须输入页面访问密码
- 进入文件管理器后，上传文件无需密码
- 预览、下载、删除都需要独立密码，并在认证成功后持续有效 1 周
- 管理后台可修改各类密码与会话时长
- 文件列表界面更美观、更整洁，支持自动发现 `down/` 目录新文件
- 提升整体安全性，同时保持部署简单

## 2. 非目标

本阶段不做以下内容：

- 不引入前后端分离架构
- 不引入数据库
- 不做复杂用户系统、角色系统和多用户审计
- 不依赖云对象存储
- 不强制引入 Docker 作为唯一部署方式

## 3. 总体方案

应用继续保持单进程 Flask 服务，目录式管理 `down/` 中的文件。通过模块拆分将原有单文件逻辑重构为认证层、配置层、文件服务层、预览层、后台设置层和前端模板层。

建议目录结构如下：

```text
downcent/
  app.py
  netu_app/
    __init__.py
    auth.py
    config.py
    file_service.py
    preview_service.py
    admin_routes.py
    main_routes.py
    security.py
    templates/
      login.html
      index.html
      admin.html
      preview_shell.html
    static/
      app.css
      app.js
      admin.js
  down/
  .passwords.yaml
  .env.example
```

部署方式仍然保持简单：

- 默认使用 `python app.py` 启动
- 支持通过环境变量或配置文件修改端口、目录、cookie 持续时间、安全参数
- 可选配合 Nginx/Caddy 反向代理使用 HTTPS，但不是运行前置条件

## 4. 权限与认证设计

### 4.1 权限模型

本次改造将权限拆成 5 类能力：

- `open`：进入首页和读取文件列表
- `preview`：在线预览文件
- `download`：下载文件
- `delete`：删除文件
- `admin`：进入后台和修改配置

上传按用户要求默认不需要密码，但仍需要服务端做文件名、类型和大小校验。

### 4.2 认证体验

- 用户打开首页时，如果没有 `open` 会话，则跳转登录页
- 用户点击预览、下载、删除时，如果没有对应能力会话，则弹出密码框
- 对应密码验证成功后，写入独立能力 cookie
- cookie 默认有效期为 `7 天`
- 后台允许修改 cookie 持续时间，例如改为 `1 天 / 3 天 / 7 天 / 30 天`
- 用户主动登出时，清除全部能力 cookie

### 4.3 密码存储

现有明文密码配置将改造成“带盐哈希存储”，推荐使用标准库 `hashlib.pbkdf2_hmac`，避免增加难部署的额外依赖。

建议配置结构：

```yaml
security:
  cookie_ttl_days: 7
  secret_key: "${NETU_SECRET}"
passwords:
  open:
    hash: "pbkdf2_sha256$240000$<salt>$<hash>"
  preview:
    hash: "pbkdf2_sha256$240000$<salt>$<hash>"
  download:
    hash: "pbkdf2_sha256$240000$<salt>$<hash>"
  delete:
    hash: "pbkdf2_sha256$240000$<salt>$<hash>"
  admin:
    hash: "pbkdf2_sha256$240000$<salt>$<hash>"
```

兼容策略：

- 首次启动时，如发现旧版明文结构，则自动迁移为哈希结构
- 迁移完成后覆写原配置文件
- 后台改密码时，始终写入哈希，不再保存明文

### 4.4 会话与 Cookie

每种能力发一个独立签名 token，而不是把原密码或简单密码派生值直接写入 cookie。

token 内容建议包括：

- 能力类型
- 过期时间
- 当前密码版本号
- HMAC 签名

设计效果：

- 修改某类密码后，对应能力旧 token 立即失效
- 修改 cookie 持续时间后，新会话按新策略生效
- 服务端无需数据库即可完成校验

Cookie 属性：

- `HttpOnly = true`
- `SameSite = Lax`
- `Secure = true`，当处于 HTTPS 时启用
- `Path = /`

### 4.5 防爆破与限流

- 登录失败按 `IP + 能力类型` 单独计数
- 默认 5 次失败后锁定 60 秒
- 后台可调整最大尝试次数和锁定时间
- 对上传接口增加基础限速与文件大小限制

## 5. 文件服务设计

### 5.1 目录扫描

服务端继续以 `down/` 作为唯一文件根目录，并在每次读取列表时扫描该目录当前内容。

扫描规则：

- 只展示文件，不展示子目录
- 忽略隐藏文件和服务内部保留文件
- 返回文件名、大小、更新时间、扩展名、MIME、预览能力信息

新增变化检测机制：

- 为文件列表计算目录快照摘要
- 前端定时轮询 `GET /api/files?since=<etag>`
- 如果目录内容变化，服务端返回最新列表和新的 `etag`
- 如果目录无变化，返回轻量响应

这样可以满足“实时扫描”而无需引入文件系统监听器，兼顾稳定性和部署简单。

### 5.2 文件名与路径安全

所有文件读写都必须经过统一安全函数处理：

- 基于 `Path.resolve()` 校验目标路径必须位于 `DOWN_DIR` 内
- 拒绝路径穿越
- 删除时必须再次确认目标文件存在且为普通文件
- 上传时对文件名做清洗，避免特殊字符和控制字符
- 已存在文件采用“安全重命名”策略，例如 `name_20260630_153012.ext`

## 6. 在线预览设计

用户要求“尽量全都预览”，但要兼顾安全，因此采用“分级预览”策略。

### 6.1 直接预览类型

以下类型走原生或安全容器直接预览：

- 图片：`jpg` `jpeg` `png` `gif` `webp` `svg`
- PDF：浏览器内嵌或 PDF.js
- 音频：`mp3` `wav` `ogg`
- 视频：`mp4` `webm` `mov`
- 文本：`txt` `md` `json` `csv` `log` `py` `js` `css` 的文本视图

### 6.2 HTML 预览策略

HTML 文件需要特别处理，不能直接以应用同源权限执行未受信任脚本。

HTML 的预览分为两种模式：

- 默认模式：安全渲染预览，用于尽量保留原页面视觉效果
- 回退模式：源码文本视图，用于安全要求更高或渲染失败时查看内容

采用以下策略：

- 默认提供“安全预览模式”
- 服务端读取 HTML 内容后，以受限响应头返回
- 预览页使用 `iframe sandbox` 承载
- 添加严格 `Content-Security-Policy`
- 默认禁止该 HTML 访问应用后台接口、读取 cookie、提交顶层跳转

这样可以尽量满足 HTML 在线查看，同时显著降低 XSS 风险。

### 6.3 Office 文档预览策略

对 `doc/docx/xls/xlsx/ppt/pptx` 采用分层降级：

- 如果系统检测到本地转换能力，例如 LibreOffice，可后台转换为 PDF 后预览
- 若未安装转换能力，则显示文件元信息页，并提供下载
- 后续可选增加 Mammoth、SheetJS 等轻依赖解析器，但不作为第一阶段强制要求

这意味着“尽量预览”会优先覆盖常见多媒体、PDF、文本和 HTML；Office 在有本地转换器时可获得最佳体验，无转换器时仍可稳定下载。

## 7. 前端界面设计

界面保持当前深色风格，但进行结构化优化。

### 7.1 首页布局

首页分为 4 个区域：

- 顶部：标题、当前目录、文件统计、刷新状态、登出入口
- 中部操作栏：搜索框、类型筛选、排序方式
- 上传区：拖拽上传、点击上传、进度条、限制说明
- 文件区：响应式文件卡片或表格式列表

### 7.2 文件项信息

每个文件项显示：

- 文件图标
- 文件名
- 类型标签
- 文件大小
- 最后修改时间
- 操作按钮：预览、下载、删除

### 7.3 状态反馈

- 上传显示真实进度
- 新文件自动插入列表并高亮短暂提示
- 删除成功后即时移除列表项
- 权限缺失时弹出对应密码框，而不是直接跳整页
- 失败、锁定、超时等状态使用统一 toast 提示

### 7.4 自动刷新体验

前端默认每 5 秒轮询一次文件列表变更摘要：

- 发现新文件时自动更新列表
- 若用户当前正在上传，则暂停自动刷新，避免界面抖动
- 若用户正在输入搜索条件，则保持过滤状态不丢失

## 8. 后台设置设计

后台提供以下配置能力：

- 修改 `open / preview / download / delete / admin` 密码
- 修改 cookie 持续时间
- 修改失败锁定参数
- 查看当前文件目录、服务端口、配置文件位置
- 查看最近目录扫描时间和文件数量

后台不显示当前密码明文，只允许直接覆盖写入新密码。

## 9. 安全基线

第一阶段必须落实以下安全项：

- 哈希存储密码
- 所有文件路径统一做根目录约束
- 上传文件名清洗
- 后台和能力 cookie 使用签名 token
- 对预览响应按类型设置 `Content-Type`
- 对 HTML 预览启用严格 CSP 与 sandbox
- 对下载响应添加 `X-Content-Type-Options: nosniff`
- 关闭调试模式，禁止在启动日志中打印密码
- 统一错误处理，避免向前端回显堆栈

推荐同时补充：

- `Cache-Control: no-store` 用于登录页、后台页和敏感接口
- `Referrer-Policy: same-origin`
- `X-Frame-Options: SAMEORIGIN`，对非 HTML 预览页生效

## 10. 接口草案

建议保留并规范化如下接口：

- `GET /login`
- `POST /login`
- `POST /logout`
- `GET /`
- `GET /api/files`
- `POST /api/upload`
- `POST /api/delete`
- `GET /download/<filename>`
- `GET /preview/<filename>`
- `GET /view/<filename>`
- `GET /admin`
- `POST /admin/api/passwords`
- `POST /admin/api/security`

接口行为约定：

- 所有数据类 API 统一返回 JSON 结构，页面路由继续返回 HTML
- 权限不足时返回 `401 + need_auth`
- 路径非法返回 `403`
- 文件不存在返回 `404`
- 校验失败返回明确但不过度暴露内部信息的错误消息

## 11. 实施分阶段

建议分 4 步完成：

### 阶段 1：代码解耦与配置迁移

- 拆分模块
- 移除重复后台路由实现
- 将写死目录改为配置项
- 增加旧密码结构迁移逻辑

### 阶段 2：认证与安全加固

- 实现新的密码哈希
- 实现能力 token
- 修复删除权限边界
- 增加安全响应头和错误处理

### 阶段 3：文件列表与预览重做

- 重构主页模板和静态资源
- 增加自动刷新、搜索、筛选和状态提示
- 实现分级预览

### 阶段 4：后台与验证

- 完成后台设置页面
- 加入基础测试
- 做部署验证和回归检查

## 12. 测试策略

测试覆盖以下核心场景：

- 首次访问必须输入 `open` 密码
- 上传无需密码，且不会写出越界路径
- 预览需要 `preview` 密码
- 下载需要 `download` 密码
- 删除需要 `delete` 密码
- 修改某类密码后，旧 cookie 立即失效
- 新文件加入 `down/` 后能被前端自动发现
- HTML 文件在安全预览下不会读取站点 cookie
- Office 文件在无转换器场景下能正确降级到下载

测试形式：

- 单元测试：密码校验、token、路径校验、文件名清洗
- 接口测试：登录、上传、下载、删除、后台改密
- 手工验证：多文件类型预览、自动刷新、移动端界面

## 13. 风险与折中

主要风险如下：

- HTML 在线预览天然有较高安全风险，因此必须通过沙箱和 CSP 明确限制
- Office 文档“尽量预览”受本机依赖影响，是否安装 LibreOffice 会影响体验
- 纯轮询方案不如 WebSocket 或文件监听实时，但稳定且更易部署

本设计明确优先级：

- 第一优先级是安全与部署稳定
- 第二优先级是常见文件类型的预览体验
- 第三优先级是全格式极致预览覆盖

## 14. 验收标准

改造完成后，应满足以下验收条件：

- 用户访问首页时必须先通过访问密码验证
- 上传文件不要求密码
- 预览、下载、删除均需独立密码并支持 1 周免重复输入
- 后台可修改密码和 cookie 持续时间
- 新文件放入 `down/` 目录后，文件列表可自动发现并展示
- 常见图片、PDF、音视频、文本文件可在线预览
- HTML 文件可在安全隔离模式下预览
- Office 文件在有转换器时可预览，无转换器时稳定降级
- 服务可通过单机 Flask 直接部署运行
